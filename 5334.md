# Plan: Classifiers (akka-runtime #5334)

Branch: `ticket/5334` in both `akka-sdk` and `akka-runtime`. Both are currently at the
`feature/governance` merge point — no classifier code exists yet on either side.

## 1. Context (so this doc is self-contained)

- **[#5407](https://github.com/lightbend/akka-runtime/issues/5407) Epic: Governance controls** —

- **[#5334](https://github.com/lightbend/akka-runtime/issues/5334) Classifiers** — this ticket.
  Sibling to #5241 (enhanced guardrails, merged), #5327 (evaluations), #5252, under #5323.

### What v1 needs from Classifiers specifically

> A classifier classifies an input and produces a classification — a score and/or label, with
> optional confidence and metadata. It can be implemented as rules/regex, embeddings, traditional
> ML, a small specialised model, a prompted/fine-tuned LLM, or an external API — all just user
> code calling out to whatever it needs; there's nothing to build per implementation type.
> Classifiers are cross-cutting: used inline from a guardrail, an evaluator, or application code
> via an injectable client. The classification is recorded as a ledger record, and marked with
> evaluation origin when produced within an evaluation.

Ticket's own task list:
- [ ] Decide the construct shape — lightweight and guardrail-like, or a full component
- [ ] Define and invoke a classifier — an injectable classifier client, callable from a guardrail,
      an evaluator, or application code
- [ ] Classification result shape — score and/or label, optional confidence and metadata
- [ ] Record classifications — as ledger record, marked with evaluation origin when produced
      within an evaluation

The one comment on the ticket (Patrik) gives example controls a classifier must be able to serve:

> - `eu-ai-act.art10.2.f-inline` [EU AI Act] — a protected-attribute **bias classifier** run on
>   each response.
> - `texas-traiga.sec552-052.intentional-discrimination-prohibition` [Texas TRAIGA] — a
>   discrimination classifier.
> - `finos-ccc-genai.cn01` [FINOS CCC GenAI] — input classification/filtering before the model.

"Run on each response" and "before the model" read push-style, but both are exactly the "used
inline from a guardrail" case: the *binding* to a boundary comes from a guardrail (or an
evaluator trigger), and the classifier is the pulled primitive inside it. #5407's generator emits
a thin wrapper guardrail + classifier pair. This resolves the construct-shape question — see §2.1.

### The three existing shapes to design against

Three governance constructs already exist in the SDK, each a different point on the
lightweight↔heavyweight spectrum. Classifiers are positioned relative to all three.

**Guardrail** (just landed, #5241) — user-implemented, config-instantiated, runtime-dispatched.
[`Guardrail.java`](akka-javasdk/src/main/java/akka/javasdk/agent/Guardrail.java) is a sealed
interface (`TextGuardrail | ToolGuardrail | ModelGuardrail`). A user class gets a public
constructor optionally taking `GuardrailContext` (name + config section), is instantiated by
`GuardrailProvider` via reflection from HOCON (`akka.javasdk.agent.guardrails { "name" { class =
..., agents = [...], use-for = [...] } }`), and is invoked *by the runtime* at a fixed boundary
(model-request/response, before-tool-call). `decide(CallContext): Decision` where `Decision` is
`Allow | Deny | Fail(reason, cause)`. Not injectable into arbitrary user code — it's config-bound
and boundary-triggered, never looked up by name from application code. Still synchronous
(`decide` returns `Decision`, not `CompletionStage<Decision>`) — a known FIXME
([ToolGuardrail.java:57](akka-javasdk/src/main/java/akka/javasdk/agent/ToolGuardrail.java#L57))
because user code inside a guardrail may need to do async work and the SPI (`SpiAgent.Guardrail
.evaluate`) is already `Future`-based underneath.

**Sanitizer** — declarative config, runtime-implemented, thin injectable client.
[`Sanitizer.java`](akka-javasdk/src/main/java/akka/javasdk/Sanitizer.java) is a single
`@DoNotInherit` interface with one method, `sanitize(String): String`. All the actual logic
(regex patterns, predefined PII detectors) lives in the *runtime* behind `SpiSanitizerEngine`;
the SDK side ([`Sanitization.scala`](akka-javasdk/src/main/scala/akka/javasdk/impl/Sanitization.scala))
just parses `akka.javasdk.sanitization.{regex-sanitizers,predefined-sanitizers}` config into SPI
settings and hands back a thin wrapper. `Sanitizer` is injected into any component's constructor
via the SDK's general dependency-resolution partial function (a fixed match on `classOf[Sanitizer]`
in `SdkRunner.scala`), same mechanism used for `ComponentClient`, `Tracing`, etc.

**Evaluator** — full component, runtime-discovered, async-triggered. Already has SDK-visible
config (`akka.javasdk.agent.evaluators { toxicity-evaluator { model-provider = ... } }`,
[reference.conf:200](akka-javasdk/src/main/resources/reference.conf#L200)) and a real runtime SPI
(`SpiEvaluator` in `akka-runtime`). On the runtime side an evaluator is a cluster-sharded,
event-sourced entity (`EvaluatorEntity`), one instance per evaluation
(`SpiEvaluator.FactoryContext(evaluationId)`), triggered asynchronously off the interaction log
via a `Trigger(id, source: Manual|OnInteraction, subject: FlowInteraction|AgentInteraction)`
that references the triggering interaction by a stable `interactionId` rather than carrying the
full payload. Its result shape (`Evaluation(passed, explanation, score, label, attributes)`,
[SpiEvaluator.scala:92-97](../akka-runtime/protocols/akka-sdk-spi/src/main/scala/akka/runtime/sdk/spi/SpiEvaluator.scala#L92))
overlaps `Classification`'s fields, but that's an SPI type, not public API — see §2.2.

### Interaction log / ledger mechanics (akka-runtime)

- Interactions persist as `InteractionAdded` / `CoordinationAdded` proto events
  ([agent.proto](../akka-runtime/runtime/core/src/main/proto/kalix/proxy/agent.proto)) on one of
  two shared event-sourced entity types: `request-agent-log` (request-based agents) or
  `autonomous-agent-log` (keyed by flowId). A secondary JSONB `query_meta` column
  (`AgentInteractionLogQueryMetaColumn`) carries `componentId` / `recordType` / `recordId` for
  GIN-indexed queries.
- **There is no separate "evaluation origin" marker.** Origin is carried by the existing
  `spiffe_id` field already present on both event types, populated per-producer via
  `SpiSpiffeContext`. An `Evaluator` entity has its own component identity distinct from the
  agent it evaluates, so anything it writes already lands with a different `spiffe_id` than the
  agent's own interactions — origin should fall out of the existing identity plumbing for free
  (**assumption — verified by a tripwire test in Phase 4**, see §4 and §5).
- No `Classifier`, `Classification`, or extensible "ledger" abstraction exists anywhere in
  akka-runtime today (confirmed by search — `DeploymentLedger` is an unrelated cluster-singleton
  for deployment state). This is a clean-slate addition on the runtime side too.

## 2. Design decisions

Decisions previously listed as open questions 3.1–3.5 are now resolved inline; each newly-made
assumption is marked **Assumption** and carries its verification plan.

### 2.1 Construct shape: lightweight, guardrail-like, pull-only — not a full component

An `Evaluator` is heavyweight because it *needs* to be: it's independently triggered off the
interaction log, needs durable per-evaluation state to survive crashes mid-evaluation, and is
explicitly decoupled from the agent's own process. A classifier has none of those requirements —
it's called *inline*, in the caller's flow, with a guardrail's latency budget. So: **Classifier
follows the Guardrail shape** (user-implemented interface, optional constructor context, no
persistent entity identity of its own), not the Evaluator shape.

Unlike Guardrail it is **pull-only**: callers invoke it explicitly; it is never boundary-bound or
runtime-dispatched. Patrik's ticket comment ("bias classifier run on each response", "input
classification before the model") is served by a thin wrapper guardrail that calls the classifier
— boundary binding stays the guardrail's job, and #5407's generator emits the wrapper.

> **Assumption (design-level):** no classifier is ever auto-attached to a boundary by config
> alone; a wrapper guardrail (hand-written or generated) is always acceptable. If product later
> wants zero-code boundary attachment, that becomes a new guardrail *implementation* shipping
> with the SDK (a `ClassifierGuardrail` that wraps a named classifier + threshold, pure config) —
> an additive change that doesn't disturb this construct. Confirm with Peter/Patrik at Phase 0.

### 2.2 API shape

```java
package akka.javasdk.agent;

/**
 * Instantiated once at startup from config; instances are shared across concurrent
 * calls and must be thread-safe.
 */
public interface Classifier {
  CompletionStage<Classification> classify(String input);
}
```

- **Async from day one.** Guardrail's `decide()` is stuck synchronous with an open FIXME; don't
  repeat that here — classifiers are explicitly expected to call out to embeddings/ML
  services/LLMs, i.e. async is the common case.
- **`String` input, not generic `<T>`** *(revised from the first draft)*. Every implementation
  strategy the ticket lists (regex, embeddings, ML, LLM, external API) consumes text, and
  tool-call arguments are already raw JSON strings in the guardrail API
  (`ToolGuardrail.CallContext.arguments()`). A generic `<T>` buys nothing concrete in v1 and
  creates a type-safety hole: with name-based lookup there is no static connection between the
  call site's `T` and what the named implementation expects. `String` also makes digest-based
  recording (§2.4) trivial. If structured input ever matters, add a sealed content hierarchy then
  — an additive change, following `SpiAgent.Guardrail.Content`'s precedent.
- Constructor: optionally takes a `ClassifierContext` (name, config section, and a
  `ClassifierClient`), mirroring `GuardrailContext`. Composition (ensembles) goes through
  `ClassifierContext.classifierClient()` — the reflection path tries only the
  `(ClassifierContext)` constructor then `()`, deliberately not a bare `ClassifierClient`
  parameter, keeping one context-object idiom across guardrails and classifiers. Lookup cycles
  fail with a clear error at wiring time, not a stack overflow.

> **⚠ Known gap:** those two constructor shapes are the *only* injection classifiers get — no
> `HttpClientProvider`, no `ComponentClient`, no user `DependencyProvider` — even though calling
> out to external services is the primary classifier use case. See §2.7 for the full analysis
> and the proposed fix.

```java
public record Classification(
    Optional<Double> score,
    Optional<String> label,
    Optional<Double> confidence,
    Map<String, String> metadata) {}
```

Directly mirrors the ticket's wording ("score and/or label, optional confidence and metadata").
A classifier doesn't render a pass/fail verdict — that's a guardrail's or evaluator's job.

*(Resolved, was open question 3.1)* The field overlap with `SpiEvaluator.Evaluation` is a
non-issue: `Evaluation` is an SPI type, `Classification` is public API, and this codebase never
shares types across that boundary (`Decision` maps to `SpiAgent.Guardrail.Result`, it doesn't
reuse it). No refactoring of the evaluator SPI is proposed.

*(Resolved, was open question 3.2)* Package is `akka.javasdk.agent` — the whole governance family
lives there and its config sits under `akka.javasdk.agent.*`. `Sanitizer`'s top-level placement
reflects its broader log/endpoint scope and predates the governance family; not a precedent here.

*(Resolved, was a nitpicker flag)* A class implementing both `Guardrail` and `Classifier` is
**allowed**. `Guardrail`'s sealed hierarchy and single-interface validation
([GuardrailProvider.scala:265-280](akka-javasdk/src/main/scala/akka/javasdk/impl/agent/GuardrailProvider.scala#L265))
exists to disambiguate boundary dispatch; classifiers are pulled by name, never dispatched, so no
ambiguity arises. Caveat *(tightened by Phase 3 — the original text promised overloaded
constructors, one per context, which no longer works)*: classifier construction now goes through
`wiredInstance`, which requires a **single public constructor** (the component-wide convention),
while guardrail construction still matches only `(GuardrailContext)` or `()`. A dual-purpose
class must therefore have a zero-arg constructor — a lone `(GuardrailContext)` constructor fails
classifier wiring and a lone `(ClassifierContext)` constructor fails guardrail wiring. A dual
class needing config from both roles isn't expressible; split it into two classes sharing the
logic.

### 2.3 Registration and the injectable client

**Instantiation**: same as Guardrail — HOCON declares named classifiers, each with a `class` and
free-form config, SDK reflection-instantiates them once at startup, `validate()` fails fast on
bad config:

```
akka.javasdk.agent.classifiers {
  "toxicity" {
    class = "com.example.ToxicityClassifier"
    threshold = 0.8   # classifier-specific config, opaque to the SDK
  }
}
```

No `use-for`/`agents`/`agent-roles` binding — a classifier isn't bound to a boundary or agent
set; it's a named, globally-available thing any caller can reach for. Deployment-time
swap/tuning (the governance team's velocity requirement) comes from the config indirection, same
as guardrails.

**Access** *(revised from the first draft)*: the ticket says "an injectable classifier client",
which points at the Sanitizer pattern — one client in the DI table, not per-class injection. But
a per-call `classify(name, input)` signature would make a typo'd name a first-call production
error. Instead the client is a handle resolver:

```java
public interface ClassifierClient {
  /** Throws immediately if no classifier with this name is configured. */
  Classifier classifier(String name);
}
```

Callers resolve handles in their constructor, so unknown names fail at component wiring time;
`validate()` still fails bad config at startup. How the client reaches each caller type differs,
because not everything is constructed through the same path:

- **Components** (agents, endpoints, entities, consumers, workflows, evaluators): injected the
  same way `Sanitizer` is — a fixed match in `SdkRunner.scala`'s dependency-resolution table.
- **Guardrails**: constructed by `GuardrailProvider`'s own reflection path, which never touches
  the DI table — so `GuardrailContext` grew a `classifierClient()` accessor (threaded in via a
  defaulted `GuardrailProvider` constructor parameter, leaving existing call sites untouched).
- **Classifiers themselves** (ensembles): via `ClassifierContext.classifierClient()`, see §2.2.

**Who owns classifier names.** Mechanically the name is just the HOCON key, but the design intent
is that **governance owns the namespace and code only consumes it — ideally via config, not
string literals**. #5407's generator will mint names from EvalMatrix entry IDs
(`eu-ai-act.art10.2.f-inline`, `finos-ccc-genai.cn01` per the ticket comment), and the
deployment-time-tuning requirement means the guardrail→classifier binding must be re-pointable
without rebuild. The canonical pattern is therefore a guardrail reading the classifier name from
its own config section:

```hocon
"bias check" {
  class = "com.example.ClassifierBackedGuard"
  classifier = "eu-ai-act.art10.2.f-inline"   # governance re-points this at deploy time
  ...
}
```

with `context.classifierClient().classifier(context.config().getString("classifier"))` in the
guardrail constructor. The integration test (`ClassifierBackedModelGuard`) models this pattern so
it carries into the Phase 5 docs.

### 2.4 Recording and evaluation-origin marking

*(Revised from the first draft — was open question 3.3)*: **v1 records the classification, not
the input.** The ticket says "the *classification* is recorded as a ledger record." The record
carries: classifier name, the `Classification` fields, a digest of the input, `spiffe_id`, and
the `interaction_id` it relates to when one is ambient. The content the classifier examined is
usually already in the interaction log under the log's own content-recording policy; the
classification references it rather than re-recording it. This deletes the input-redaction
question from this ticket's scope; if full input recording is ever wanted it inherits the
interaction-log recording levels (none/digest/redacted/full) later.

Mechanics — reuse the existing interaction-log entities and the existing `spiffe_id` origin
mechanism; don't invent a parallel "ledger":

- Add a `ClassificationAdded`-shaped proto event to the same shared log entities
  (`request-agent-log` / `autonomous-agent-log`), tagged in `query_meta` with
  `recordType = "classification"` so it's queryable alongside interactions with no new entity
  type or archive/export path.
- "Marked with evaluation origin when produced within an evaluation": a classification produced
  inside an `Evaluator.evaluate()` carries that evaluator's `spiffe_id`, distinct from the
  agent's.

> **Assumption (mechanism-level):** evaluator-produced records genuinely get a distinct
> `spiffe_id` from the agent under evaluation. This is plausible from `EvaluatorEntity`'s
> registration path but was **not** directly confirmed in the SPIFFE-assignment code (only
> agents/MCP endpoints were verified). Phase 4's origin test is the tripwire: if it fails, §2.4's
> "no new proto field" simplification is dead and an explicit origin field gets added to the
> proto event instead. Write that test first in Phase 4.

*(Resolved, was open question 3.5)*: the runtime needs **only** the recording SPI, no dispatch
SPI — the runtime never decides to fire a classifier. Consequence: **Phase 1 ships standalone
value** (classifiers callable from guardrails, with the guardrail's decision recorded via the
existing path) before recording lands.

> **Assumption (scope-level):** offline/batch evaluation (#5327's dataset runner, pass@k) is out
> of scope for how classifiers are obtained in v1 — `ClassifierClient` exists only inside a
> running SDK service. Since a classifier is just a plain interface + `Config`, an offline harness
> can construct implementations directly without the client; if #5327 wants config-driven lookup
> outside a running service, that's a small standalone factory to add then. Flag to #5327's owner
> at Phase 0 so it's a known limitation, not a surprise.

### 2.5 Recording enforcement and correlation (decided during Phase 1 review)

> **Partially superseded by §2.8 (design review with Peter, 2026-07-07).** The *requirements*
> below stand — every client-obtained classification ledgered, correlation to the ambient
> interaction/evaluation, failure records, ungated at-most-once delivery. The *mechanism* moves:
> interception happens runtime-side behind an SPI call (not in the SDK wrapper), and correlation
> rides OpenTelemetry baggage (the platform mechanism per
> [#5331](https://github.com/lightbend/akka-runtime/issues/5331)) rather than a bespoke SDK
> ambient scope. Read this section for the what, §2.8 for the revised where/how.

How Phases 2–3 guarantee that *every* classifier result is persisted, and linked to the ambient
interaction/task:

**Enforcement: one choke point.** `ClassifierProvider` already wraps every instance it hands out
(`wrapSafely`, currently just translating thrown exceptions into failed stages). Recording lands
in that same wrapper — no code path that obtains a classifier through the client can bypass it,
and ensembles get member-level records for free because each member lookup re-enters the wrapper.
The only escape hatch is direct instantiation (`new MyClassifier(...)`), documented as
unsupported/unrecorded — the same escape hatch guardrails have.

**Correlation: capture ambient context eagerly, at `classify()` call time, on the caller's
thread** — never at completion. The stage may complete on another executor, but a snapshot taken
before dispatch stays valid; the wrapper attaches it to the record when the stage completes.
Where the ambient context comes from differs per caller type, matching existing codebase idioms:

- **Components**: the DI table's injection closures already receive `telemetryContext` — note how
  `componentClient(telemetryContext)` constructs a per-injection instance. Phase 3 changes the
  shared `lazy val classifierClient` into `classifierClient(telemetryContext)`, per injection.
- **Guardrails**: the handle is resolved at guardrail construction, so per-call context can't be
  baked into it. But the SDK owns the call site — `ToolGuardrailAdapter`/`ModelGuardrailAdapter`
  receive the per-call content (`telemetryContext`, and for tools `sessionId`/`toolCallId`/
  `agentId`) and install an SDK-internal ambient scope around `decide()`. Trivially correct today
  *because* `decide()` is synchronous; the pending async-guardrail migration must carry a
  scoped-context story with it.
- **Evaluators**: the evaluator impl installs an `evaluationId` scope around `evaluate()` — this
  is the explicit "evaluation origin" marking, layered on the `spiffe_id` mechanism (A4).
- **Fallback** (plain application code with no interaction ambient): record with component
  identity + OTel trace/span id only — §2.4's "when one is ambient" wording already allows this,
  and the trace id still provides a join key.

**The pipeline, concretely.** What the recording wrapper in `ClassifierProvider` does on every
`classify(input)` call:

1. Snapshot the ambient recording scope **on the caller's thread**: origin kind
   (`agent | guardrail(name, boundary) | evaluator(evaluationId) | application`), `componentId`,
   `sessionId`/`flowId` and `interactionId` when present, `spiffe_id`, OTel trace/span ids.
2. Mint a `classificationId` (UUID) and take the start timestamp.
3. Invoke the delegate (thrown exceptions become a failed stage — the existing `wrapSafely`
   behaviour).
4. On stage completion — success **or failure** — hand a `SpiClassificationRecord` to the
   recorder. A failed classification is itself a governance-relevant event (it's what a
   fail-closed guardrail acted on), so failures are ledgered with the exception class + reason
   in place of the classification fields.
5. Return the delegate's stage to the caller **unmodified** — the caller's `classify()` is not
   gated on the ledger write (see delivery semantics below).

**Record schema** (`ClassificationAdded` proto event / `SpiClassificationRecord`):

| group | fields |
|---|---|
| identity | `classification_id`, `classifier_name`, `classifier_class` |
| input | `input_digest` (SHA-256), `input_length` — never content, per §2.4 |
| outcome | `score?`, `label?`, `confidence?`, `metadata{}` — or `failure_reason` + exception class |
| timing | `started_at`, `completed_at` |
| correlation | `component_id`, `session_id?`, `flow_id?`, `interaction_id?`, `evaluation_id?`, `guardrail_name?` + boundary, `spiffe_id`, `trace_id`/`span_id`, `parent_classification_id?` (open, see below) |

`origin` is not a separate field — it's derivable from which correlation ids are set
(`evaluation_id` ⇒ evaluation origin, `guardrail_name` ⇒ guardrail, neither ⇒ application), plus
`spiffe_id` for the producer identity (A4).

**Routing — where the record physically lands.** The SDK never picks an entity; it hands the
record + correlation snapshot to the runtime, which routes:

- `sessionId` ambient → the `request-agent-log` entity for that session, appended to the same
  journal as the interactions it relates to, `query_meta.recordType = "classification"`.
- `flowId` ambient → the `autonomous-agent-log` entity for that flow, ditto.
- neither (plain application code) → a **new shared log entity type, `classification-log`, keyed
  by `componentId`**. This is the piece the original "reuse the existing entities" wording
  glossed over: app-code classifications have no session or flow to attach to, and "all results
  are persisted" means they need a home too. Same journal/exporter/archive machinery, one new
  entity type. (If a single per-component entity ever becomes a write hotspot, shard the key by
  time bucket — noted, not built, for v1.)

**Delivery semantics (v1): asynchronous, at-most-once.** The recorder buffers (bounded) and
writes without gating the caller's stage. A write failure or buffer overflow logs an error and
bumps a `classification_records_dropped` counter; it never fails the classification. This
matches the interaction log's own posture — the agent's response isn't gated on `InteractionAdded`
landing either, so classifications are exactly as durable as the interactions they annotate. Two
deliberate consequences, stated so nobody discovers them later: (a) a crash between acting on a
classification and the write landing loses the record; (b) there is no intent-then-result pair
for classifications — that machinery is reserved for side-effecting tool calls, and `classify()`
is read-only by contract. If a control ever demands classification-before-action durability, the
upgrade path is a per-classifier config knob (`record-delivery = gated`) that completes the
caller's stage only after the ledger ack — additive, not v1.

**Recorder wiring detail**: `ClassifierProvider` is constructed (and `validate()` runs) before
the runtime handshake completes, so the recorder arrives as a lazy thunk from `StartupContext` —
same pattern as `runtimeSanitizer`. Records produced before the runtime is ready cannot happen:
`classify()` is only reachable from constructed components, which the runtime starts after
handshake.

**Runtime SPI gaps this exposes** (Phase 2 scope, beyond the `ClassificationAdded` event itself):

1. `SpiAgent.Guardrail.TextContent` carries only text + telemetry context — no `interactionId`,
   and model-side guardrails don't even get `sessionId` (only `ToolCallContent` has it). The
   promised `interaction_id` linkage needs `interactionId` added to guardrail content in the SPI.
2. The recorder SPI: `SpiClassificationRecorder.record(SpiClassificationRecord): Unit`
   (fire-and-forget from the SDK's view; buffering and routing live runtime-side), delivered via
   `StartupContext`.
3. The `classification-log` shared entity type for sessionless records (routing table above).

Open sub-decision for Phase 2: whether ensemble member classifications are recorded flat, or
with a parent/child link to the top-level classification (a `parent_classification_id` field).
Flat is simpler and probably enough for v1 — member records still share the same interaction
linkage. Leaning: include the field in the proto (cheap now, breaking later), populate it via
the ambient scope (an in-flight classification pushes its id onto the scope, so nested
`classify()` calls pick it up automatically through the same snapshot mechanism as everything
else), but build no query features on it in v1.

### 2.6 The design, code-first

The whole construct in one worked example — implement, define, bind, look up, invoke. The API is
the Phase 1 code as landed; the under-the-hood ledger comments describe Phase 3 behaviour.

**1. Implement a classifier** — plain user code; an external API here, but regex, embeddings, a
local ONNX model, or an LLM call are equally valid. Nothing to extend beyond the one interface:

```java
/** Labels text for protected-attribute bias (EU AI Act art. 10.2(f)). */
public class BiasClassifier implements Classifier {

  // Plain JDK client, NOT the SDK's HttpClientProvider: classifier constructors are outside
  // the DI table today -- only (ClassifierContext) or () can be injected. The fix (route
  // construction through wiredInstance, §2.7) is confirmed for classifiers and lands with
  // Phase 3, after which `BiasClassifier(ClassifierContext ctx, HttpClientProvider http)`
  // works like any component constructor.
  private final HttpClient http = HttpClient.newHttpClient();
  private final URI endpoint;
  private final double threshold;

  // Optional constructor param. name() is the config key ("eu-ai-act.art10.2.f-inline" below);
  // config() is this classifier's own section; classifierClient() would let an ensemble
  // classifier resolve and combine other classifiers.
  public BiasClassifier(ClassifierContext context) {
    this.endpoint = URI.create(context.config().getString("endpoint"));
    this.threshold = context.config().getDouble("threshold");
  }

  // Async by contract: instances are startup singletons shared across concurrent calls,
  // must be thread-safe, and must not have side effects (classify is read-only).
  @Override
  public CompletionStage<Classification> classify(String input) {
    var request =
        HttpRequest.newBuilder(endpoint).POST(BodyPublishers.ofString(input)).build();
    return http.sendAsync(request, BodyHandlers.ofString())
        .thenApply(
            response -> {
              double score = Double.parseDouble(response.body());
              String label = score >= threshold ? "biased" : "unbiased";
              return new Classification(
                  Optional.of(score),
                  Optional.of(label),
                  Optional.empty(),                  // confidence: this scorer has none
                  Map.of("model", "bias-scorer-v2")); // free-form metadata, ledgered as-is
            });
  }
}
```

namespace (EvalMatrix entry ids, per #5407):

```java
public class ClassifierBackedGuard implements ModelGuardrail {
  private final Classifier classifier;

  public ClassifierBackedGuard(GuardrailContext context) {
    // Resolved at wiring time: a typo'd name fails startup, not a 3am production request.
    this.classifier =
        context.classifierClient().classifier(context.config().getString("classifier"));
  }

  @Override
  public Decision decide(CallContext ctx) {
    // decide() is synchronous today (known FIXME), so block on the stage.
    var c = classifier.classify(ctx.text()).toCompletableFuture().join();
    return c.label().filter("biased"::equals).isPresent()
        ? new Decision.Deny("response withheld: protected-attribute bias detected")
        : new Decision.Allow();
  }
}
```

**4 + 5. Programmatic lookup and a call from application code** — `ClassifierClient` injects
into any component (agent, endpoint, entity, consumer, workflow), same as `Sanitizer`:

```java
@HttpEndpoint("/loan")
public class LoanEndpoint {
  private final Classifier bias;

  public LoanEndpoint(ClassifierClient classifiers) {
    // Handle resolution, not per-call lookup: unknown name -> component wiring fails.
    this.bias = classifiers.classifier("eu-ai-act.art10.2.f-inline");
  }

  @Post("/explain")
  public String explain(String recommendation) {
    // Under the hood (§2.8 architecture), the handle delegates through the SPI into the
    // runtime, so this call:
    //  1. crosses into the runtime's classifier interceptor, which reads the ambient OTel
    //     context -- trace/span ids, and any flow id / evaluation id riding OTel baggage
    //     (none here: plain application code) -- and mints a classification_id;
    //  2. opens a span, then invokes the registered classifier (this BiasClassifier instance)
    //     -- a thrown exception becomes a failed stage;
    //  3. on completion (success OR failure) writes a classification record to the ledger --
    //     input digest + length (never content), score/label/metadata or failure reason,
    //     timings, correlation ids -- fire-and-forget, routed by the runtime's shared ledger
    //     machinery;
    //  4. returns the stage ungated -- we act on the result without waiting for the ledger,
    //     so the record is exactly as durable as any other ledger record (at-most-once).
    var classification = bias.classify(recommendation).toCompletableFuture().join();

    if (classification.label().filter("biased"::equals).isPresent()) {
      return "recommendation withheld pending review";
    }
    return recommendation;
  }
}
```

The same `classify()` call made inside `ClassifierBackedGuard.decide()` above ledgers
differently only in its correlation: the flow/session context is ambient in the runtime when the
guardrail fires, so that record carries `session_id`, `interaction_id`, and
`guardrail_name = "bias check"` — and one made inside an `Evaluator.evaluate()` picks up the
`evaluation_id` from OTel baggage (#5331), which is what marks it as evaluation-origin.

### 2.7 ⚠ Constructor-injection gap: classifiers are built outside the DI table

`ClassifierProvider` constructs classifiers with `dynamicAccess.createInstanceFor`, trying
exactly two constructor shapes: `(ClassifierContext)` and `()`. Nothing else can be injected —
no `HttpClientProvider`, no `ComponentClient`, no `Materializer`, no lookups from the user's
`DependencyProvider`. §2.6's example uses the plain JDK `HttpClient` precisely because the SDK's
instrumented client is unreachable from a classifier constructor.

Guardrails have the identical limitation (`GuardrailProvider.createGuardrail` is the same
`dynamicAccess` pattern with a fixed argument list) — the gap is inherited, not newly created —
but classifiers feel it harder: "user code calling out to whatever it needs" (an embeddings
service, an external classification API, an LLM) is the ticket's *primary* use case for the
construct, not an edge.

Consequences today:

- outbound calls from a classifier go through hand-rolled clients, invisible to the SDK's
  tracing/metrics instrumentation — they won't parent under the interaction's trace;
- users whose API clients are managed by their `DependencyProvider` (the Spring-style setup)
  can't reach them from a classifier.

Options, grounded in the DI practices the SDK already has:

1. **Route construction through `wiredInstance` (recommended).** The SDK already owns a general
   constructor-wiring mechanism: `wiredInstance(clz){ partialFunction }`, backed by
   `sideEffectingComponentInjects` (ComponentClient, HttpClientProvider, GrpcClientProvider,
   TimerScheduler, Materializer, Retries, AgentRegistry, Executor, Sanitizer, ClassifierClient,
   Meter, ObjectStorageProvider), a `Config` fallback, and the user `DependencyProvider` as the
   catch-all — it's how endpoints, consumers, and `ServiceSetup` are constructed. Building
   classifiers the same way, with `case c if c == classOf[ClassifierContext] => context`
   prepended to the partial function, lets a classifier declare
   `BiasClassifier(ClassifierContext ctx, HttpClientProvider http)` like any component.
   Mechanics: `ClassifierProvider` today receives only `system` + config; it would additionally
   take the injection partial function from `Sdk`. The matching change should land in
   `GuardrailProvider` at the same time so the two constructs don't diverge — coordinate with
   the #5241 owners.
2. **Grow `ClassifierContext` accessor-by-accessor** — the `GuardrailContext.classifierClient()`
   precedent: add `httpClientProvider()` etc. to the context as needs appear. Fine for a single
   well-motivated addition, but it re-derives the DI table piecemeal and every new dependency is
   a public API change. Rejected as the general answer.
3. **Status quo for v1** — the ticket's own framing is "all just user code calling out to
   whatever they need", and plain JDK/vendor clients do work. Acceptable short-term at the cost
   of the two consequences above.

One caveat survives even option 1: classifiers are **startup singletons**, so per-call telemetry
context can't be baked in at construction the way per-request endpoints get it (their
`HttpClientProvider` is created per-injection with the request's `telemetryContext`; a
classifier's would be created once with none). Correct trace parenting for classifier-internal
calls depends on getting the per-call context to the classifier *some other way* — and, per the
codebase's own idiom (confirmed in the Phase 2.1 review: `Context.current()`/`makeCurrent()` has
zero occurrences anywhere in akka-runtime, context is always threaded explicitly, e.g.
`SpiAgent.Guardrail.Content.telemetryContext`), that's not an ambient scope. `SpiClassifier
.classify` now takes an explicit `telemetryContext` parameter carrying the classifier's own span
as current (Phase 2); Phase 3's remaining piece is exposing that to the *user's* classifier
implementation via a `Tracing`-style handle on `Classifier`'s public per-call API, mirroring
`ModelGuardrail.CallContext.tracing()` — not yet done, since `Classifier.classify(String)` has no
per-call context parameter today.

**Decision (revised in §2.8): implement (1), for classifiers only.** Peter confirmed full
dependency injection into classifiers; guardrails are explicitly left alone — they need the same
eventually, but that belongs to the separate enhanced-guardrail work (see §2.8).

> **⚠ Known limitation (found in the Phase 3 exit review, partially fixed in Phase 3.2):**
> consequence 2 above was only *partially* fixed initially. Classifiers were constructed eagerly at
> `Sdk` construction (`validate()` + SPI registration), but `ServiceSetup.createDependencyProvider()`
> only runs later, inside `preStart` — so a classifier constructor depending on a
> user-`DependencyProvider`-supplied dependency failed at startup with "no DependencyProvider was
> configured" even when the user had one. **Phase 3.2 fixed this for classifiers reached directly**
> (`spiConfiguredClassifiers` resolves lazily now; `validate()` moved into `preStart`, after
> `createDependencyProvider()`). **Still open**: a classifier resolved only inside a *guardrail's*
> constructor is unaffected by that fix — guardrail construction is forced earlier still, by agent
> descriptor building (`guardrailProvider.agentGuardrails(...)`), independent of
> `guardrailProvider.validate()`. Closing that requires deferring guardrail construction *timing*,
> flagged as a parked decision (§4) rather than folded into Phase 3.2 unilaterally.

### 2.8 Design review outcome (Peter, 2026-07-07): runtime-invoked classifiers

Peter's review reframed the invocation architecture. The construct stays in-between — not a full
component (that alternative was considered and set aside; registration-through-SPI gets
runtime-side recording and observability without per-instance entity overhead) — but it becomes
a **runtime-registered construct called through the SPI**, rather than SDK-only:

**Revised invocation flow.**

1. At startup the SDK **registers** the configured classifiers with the runtime, extending the
   existing registration precedent: `SpiComponents.guardrailSetup` already carries
   `SpiGuardrailSetup(Seq[SpiConfiguredGuardrail])` (name, implementation class, enablement,
   config) to the runtime. Classifiers register similarly, but as *invocable* entries — name plus
   an `SpiClassifier` instance wrapping the user's `Classifier` — since unlike guardrails the
   runtime must be able to be called *for* them, not just know about them.
2. `ClassifierClient.classifier(name).classify(input)` — the user-facing API is unchanged —
   delegates through an **`SpiClassifierClient`** into the runtime.
3. The runtime-side interceptor owns everything the SDK-side pipeline in §2.5 was going to do:
   - **context propagation**: flow ids and evaluation ids ride **OTel baggage** — the platform's
     chosen mechanism ([#5331](https://github.com/lightbend/akka-runtime/issues/5331): "the
     evaluation id is propagated through the evaluation, including into an LLM-as-judge agent,
     using OpenTelemetry baggage — the same approach used for flow ids"). A classification
     produced inside an evaluation picks up the evaluation id from baggage with no
     classifier-specific machinery — this *replaces* §2.5's bespoke "SDK-internal ambient scope"
     and refines A4 (evaluation origin = evaluation-id reference on the record, per #5331;
     `spiffe_id` remains producer identity);
   - **observability**: spans/metrics around each classification, aligned with how
     `AgentGuardrailInteractions` instruments guardrail evaluations and with
     [#5443](https://github.com/lightbend/akka-runtime/issues/5443) (observability for
     evaluations) — instrumentation lives runtime-side, where the platform does it everywhere
     else;
   - **ledger recording**: the runtime writes the classification record into the **ledger** (the
     go-forward name for the interaction log, records not entries —
     [#5436](https://github.com/lightbend/akka-runtime/issues/5436)), using the shared
     ledger/queue entity pattern ([#5442](https://github.com/lightbend/akka-runtime/issues/5442)).
     Classifications as a ledger record type are already anticipated on the runtime side:
     [#5330](https://github.com/lightbend/akka-runtime/issues/5330)'s ledger client lists
     "interactions, coordination, **classifications**, decisions, and even prior evaluations" as
     fetchable record kinds.

**What §2.5 keeps vs loses.** The record schema, failure-records-too, digest-not-content, and
ungated at-most-once delivery all stand. The choke point argument survives intact — it just
moves: the SPI boundary is the un-bypassable interception point for every client-obtained
classifier (direct `new` remains the documented escape hatch). What's dropped: the SDK-side
recorder thunk, the bespoke ambient-scope snapshot (→ OTel baggage), and the SDK deciding
routing — the runtime's ledger machinery owns where sessionless records land (§2.5's
`classification-log` entity question transfers to #5442's shared-pattern work).

**DI resolution (was §2.7's open decision).** Confirmed by Peter: *"we want to support any of
the dependency injection into classifiers"* — so §2.7 option 1 (`wiredInstance` routing) is in
scope for classifiers. Equally explicit: *"Guardrails should be left alone though. They do need
to support this, but that enhanced guardrail work is separate."* — the matching
`GuardrailProvider` change is **dropped** from this ticket.

**Alignment with the enhanced-guardrail work (Renato).** The in-flight work to know about, and
not collide with:

- [akka-sdk#1692](https://github.com/akka/akka-sdk/pull/1692) + runtime
  [#5420](https://github.com/lightbend/akka-runtime/pull/5420): multimodal content exposed to
  `ModelGuardrail.CallContext` (`contents()` alongside `text()`). No overlap with classifier
  files, but it touches `GuardrailProvider`/`ModelGuardrailCallContextImpl`, which Phase 1 also
  touched — expect a small merge either way.
- [#5383](https://github.com/lightbend/akka-runtime/issues/5383): async guardrails
  (`CompletionStage<Decision>`) — the tracked issue behind the FIXME this doc cites; when it
  lands, the block-on-classifier in the guardrail example becomes composition.
- [#5382](https://github.com/lightbend/akka-runtime/issues/5382): MCP tool interceptors vs
  ToolGuardrails consolidation.
- Provisional: Phase 1's `GuardrailContext.classifierClient()` accessor is how a guardrail
  reaches classifiers *today*; if enhanced-guardrail DI later gives guardrails general
  constructor injection, that accessor may become redundant — revisit then, don't extend it now.

**Phase 1 code impact.** The public API (`Classifier`, `Classification`, `ClassifierContext`,
`ClassifierClient`, the config schema) and all delivered tests survive unchanged. What gets
rewired in Phases 2–3 is internal: `ClassifierProvider` keeps construction/validation/DI, but
the client handle delegates through `SpiClassifierClient` instead of returning the locally
wrapped instance directly.

**Multimodal input note.** PR 1692 giving guardrails `contents()` puts pressure on A2
(`String` input): a guardrail inspecting image content can't hand it to a `String` classifier.
Not a v1 blocker (the listed control examples are all text), but A2's "revisit trigger" is now
concrete — if classifier-over-image-content becomes a requirement, add a sealed content
hierarchy mirroring `MessageContent`.

### 2.9 Design rationale: why a function type earns this much machinery

The devil's-advocate critique, at full strength: *a `Classifier` is
`String => CompletionStage<Classification>` — a named async function — and for it we shipped
four public API types, a config schema, reflection instantiation with cycle detection, three SPI
types, constructor changes rippling through every `SpiComponents`/`StartContext` construction
site in two repos, a runtime registry, an interceptor, spans, and a planned ledger write.
Sanitizers (`String => String`) already have their own SPI engine; guardrails
(`Content => Decision`) their own dispatch stack; evaluators a full component. When the next
function family arrives — EvalMatrix verifiers, calibration scorers, redactors — does it clone
this entire ceremony? That's N constructs × M cross-cutting concerns, all hand-integrated.*

What the critique gets right: the type is trivially a function; the SPI constructor ripple is
real and would repeat per family; and the codebase already shows the pressure at another level —
#5442 exists precisely because the ledger entity and the evaluation trigger queue turned out to
be near-duplicates worth extracting.

Where it fails: **the ceremony isn't for the function, it's for the evidence about the
function.** The platform's value is that a compliance officer can ask "was
`eu-ai-act.art10.2.f-inline` run on this response, by which implementation, with what result?"
and get an answer. A bare function can't produce that; a convention ("please remember to log")
produces it unreliably, which for audit purposes is the same as not at all. Each piece of
machinery maps to a requirement: the *name* is the unit of governance authorship and deploy-time
rebinding; the *registry + SPI choke point* is what makes recording enforced rather than
voluntary; *runtime-side interception* is where the platform already does tracing, baggage, and
ledger writes for everything else. And the counterfactual was actually run: the first design
(§2.5 v1, SDK-side wrapper, no registry, no SPI) failed review on exactly the cross-cutting
concerns — correlation needed the platform's baggage mechanism, observability the runtime's
instrumentation, recording the runtime's ledger entities. The ceremony was discovered, not
invented; there is a minimum coupling cost to participate in trace + ledger + config + DI,
whoever pays it.

On "next week", concede — and make it policy:

- **Rule of three.** The existing families genuinely differ in their load-bearing dimension
  (guardrails are boundary-dispatched, classifiers name-pulled, sanitizers runtime-implemented
  with no user code at all), so a generic mechanism designed today from one worked example would
  be either too rigid or a framework-for-frameworks. A *third* named-user-function family
  triggers extraction of the generic spine — and Phase 2 deliberately kept that extraction
  mechanical: `SpiConfiguredClassifier(name, class, config, instance)` is already just "named
  configured invocable", and `ClassifierRegistry`/`ClassifierInteractions` contain almost
  nothing classifier-specific (rename `classify` to `invoke` and it's a generic governed-function
  spine). The classifier-specific surface is deliberately thin: the `Classification` result
  shape and the Java-facing API. This mirrors #5442's own play — build the second instance as a
  knowing near-duplicate, extract with evidence of what varies.
- **The scope bar.** This treatment is earned by "governance requires evidence of this
  function's behavior" — a regulation names classifiers, which is why they cleared it. A
  function family that doesn't need name-authorship, enforced recording, and audit correlation
  should *not* get the treatment. Triage the next candidate against this bar rather than
  cargo-culting it through the pipeline.
- **The valid residue.** The constructor-ripple pain is a real criticism of the *SPI's evolution
  style* (positional final-class constructors with deprecated-overload accretion — `SpiComponents`
  is three deep), not of classifiers. If more setups are coming, `SpiComponents` wants a
  builder/`withX` shape or a single extensible governance-setup carrier — raised as a parked
  follow-up for the runtime owners, decoupled from this ticket.

## 3. Testing

### Phase 1 — unit (mirroring `GuardrailProviderSpec` / `GuardrailSettings`)

- **`ClassifierSettingsSpec`** — config parsing: missing `class` fails with a pointed message;
  blank name rejected; extra free-form keys preserved and reachable via
  `ClassifierContext.config()`; empty `classifiers {}` section is valid.
- **`ClassifierProviderSpec`** —
  - reflection instantiation with and without the `ClassifierContext` constructor;
  - configured class not implementing `Classifier` → fails at `validate()` (startup), not at
    first use;
  - `classifier(name)` with an unknown name → immediate descriptive error;
  - exception thrown *inside* `classify()` → surfaces as a failed `CompletionStage`, never a
    thrown exception escaping to the caller's thread (the `evaluateSafely` lesson from
    `GuardrailProvider`);
  - composition: a classifier constructed with `ClassifierClient` resolving another classifier
    works; a lookup **cycle** fails informatively at wiring time;
  - a class implementing both `Guardrail` and `Classifier` is accepted by both providers.
- **Thread-safety contract**: instances are startup singletons shared across calls (same as
  guardrails) — document on the interface and add a concurrent-invocation test (N parallel
  `classify` calls against a latch-instrumented classifier, asserting no cross-call state
  corruption).

### Phase 1 — integration (`akka-javasdk-tests`, following the `BlockingModelGuard` pattern)

- Test classifier configured in `application.conf`, invoked from:
  - (a) a `ModelGuardrail.decide()` that denies when the classifier's label/score crosses a
    threshold — the canonical composition, run end-to-end against `TestModelProvider`;
  - (b) an HTTP endpoint via constructor injection — proves the DI table entry works outside
    agents.
- **Async-under-sync-guardrail**: a classifier completing its stage on a different executor,
  called from the still-synchronous `Guardrail.decide()`. The guardrail must block on the stage
  for now; assert it works and note the interim limitation explicitly (this is where the
  guardrail sync FIXME bites — if the guardrail async migration lands first, this test converts).

### TestKit story (decide and document in Phase 1)

- Component unit tests: users testing an agent/guardrail/endpoint that takes `ClassifierClient`
  need it supplied — preferred approach is the real provider running from test config (cheap,
  config-driven, no fake needed); fall back to a `DependencyProvider` override where users want
  canned `Classification`s. Verify whether `TestKitSupport` wires the DI table automatically or
  needs an addition.
- User-side tests of classifier implementations themselves need nothing from us — plain
  interface + `Config`, trivially constructible. State this in the docs.

### Phases 2–3 — recording

- Runtime repo: proto round-trip for `ClassificationAdded`; `query_meta` carries
  `recordType = "classification"` and is GIN-queryable (mirror the existing
  `AgentInteractionLogQueryMetaColumn` tests).
- SDK integration: after a classify call inside an agent flow, read the interaction log back
  (backoffice/console read path) and assert the classification record exists with the correct
  `interaction_id` linkage and digest. Runs against the snapshot-pin runtime version.

### Phase 4 — origin (the design tripwire)

- Test 1: classifier invoked from inside an `Evaluator.evaluate()` → record carries the
  evaluator's `spiffe_id`.
- Test 2: same classifier invoked from a guardrail on an agent → record carries the agent's
  `spiffe_id`.
- **Write test 1 first.** If it fails because evaluators don't get distinct SPIFFE ids, the
  assumption in §2.4 collapses and an explicit origin field is added to the proto event —
  cheaper to learn this at the start of the phase than after building queries on top of it.
